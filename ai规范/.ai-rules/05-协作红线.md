> **触发场景**：任何一次让 AI 动代码之前；多模块、多服务、多人协作时尤其重要。
> **核心**：**AI 只修改明确授权的文件，其他所有内容只读。**

# 协作红线

## 一、核心原则

> 「AI 写的代码放一边，自己写的代码放另一边，永远不要在同一文件里混用。」

| 原则 | 说明 |
|---|---|
| **默认拒绝写** | 没有明确授权的路径一律不动 |
| **授权必须精确** | 用相对路径 + 具体文件/目录，不说「你看着改」 |
| **撤销要明确** | 一阶段完成就说「本次授权结束」 |
| **全局只读、局部可写** | 可以读整个仓库理解上下文，只能写授权子集 |

## 二、四条隔离

| 隔离 | 做法 |
|---|---|
| **项目目录隔离** | AI 辅助开发与人手写代码使用不同目录或不同仓库 |
| **文件隔离** | 同一项目内划分 AI 产出区与人工区，互不覆盖 |
| **分支隔离** | AI 用 `feature/ai-*`，人用 `feature/manual-*`；AI 分支不得直接合主干 |
| **工具隔离** | AI 工具与 IDE 不同时打开同一目录，用不同窗口 |

## 三、修改范围声明模板

### 基础版

```markdown
【本次权限】
- ✅ 可改：`src/handlers/order_handler.ts`、`src/schemas/order.ts`
- ❌ 不可改：`src/database.ts`、`config/` 下任何文件、`tests/`（未授权）
- ❌ 不新建文件（需要时先列路径等批准）
- 📖 可只读其他文件作为参考
```

### 微服务版

```markdown
【本次权限】
- ✅ 可写：`services/notification-service/src/`
- 📖 只读：`services/*/`、`shared-libs/`（理解接口）
- ❌ 禁写：`services/order-service/`、`services/payment-service/`
- ❌ 禁写：`docker-compose.yml`、`.env*`、CI 配置
```

## 四、反越权的四条措施

1. **禁用自动修复**：「不要自动格式化或重构现有代码，除非我明确要求。」
2. **依赖必须报批**：「需要加库时先说明理由、库名、版本、许可证，批准后才能改依赖文件。」
3. **YAGNI**：「不要添加任何未要求的功能、参数、配置项或注释。需求模糊就提问，别自己补。」
4. **高风险必问**：删除文件、改 `.env` / 配置、改迁移脚本、增删依赖——必须先问。

## 五、写权限地图（项目里必须有一份）

在项目 `AGENTS.md` 里维护三张清单，随时更新：

| 类别 | 含义 | 典型内容 |
|---|---|---|
| ✅ 可写 | AI 可直接改 | 业务代码、组件、测试 |
| ❌ 禁写 | 必须人工或逐条批准 | 核心配置、迁移脚本、CI、依赖文件、密钥 |
| 📖 只读 | 仅供理解 | 文档、其他模块、公共库 |

> 清单外的一切 = 禁写。

## 六、通用库与共享资产的特别规定

- 默认只读。确需修改时必须：说明影响范围 → 列回归清单 → 获批准 → 改完全量测试。
- 禁止为「适配自己」去改公共接口；接口不一致时报告冲突，由人决定改哪边。

## 七、版本控制保护

| 措施 | 作用 |
|---|---|
| `.gitignore` 排除 `ai-sandbox/` | AI 草稿永不进仓库 |
| 分支保护（main 只接受 PR） | 堵住直达主干的路径 |
| pre-commit 路径守卫 | 拦截 AI 分支改动受保护目录 |
| CI 路径白名单 | 越界 PR 直接失败 |
| 强制 diff / patch 落地 | 写入动作由人执行 |

## 八、三条红线（记这三条就够）

| 红线 | 含义 |
|---|---|
| ❌ **不混用** | AI 工具与人用 IDE 不同时打开同一项目 / 同一服务目录 |
| ❌ **不覆盖** | AI 永不直接改人工项目文件，只写授权目录 |
| ❌ **不盲从** | AI 产出必须经人工审查 + 手动迁移，不可直接采用 |

## 九、责任分工

| 任务 | 谁做 |
|---|---|
| 样板代码、CRUD、DTO、测试骨架 | AI 生成，人审 |
| 核心业务逻辑、异常策略、性能优化、安全加固 | 人主导 |
| 架构决策、技术选型、数据模型 | 人 |
| 第三方接口调研、方案对比、文档初稿 | AI 起草，人定稿 |

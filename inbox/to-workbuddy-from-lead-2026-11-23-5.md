## 2. 三条路线

| 路线 | 做法 | 优点 | 缺点 | 教学价值 |
|---|---|---|---|---|
| **A 黑盒** | 后端自己调工具，前端只收到最终文字 | 零契约变更、改动最小 | **用户完全看不到"工具调用"发生**，等于没学 | ⭐ |
| **B 半透明**（推荐） | 后端在 SSE 里插入"工具事件"，前端渲染成工具卡片 | 用户能看见"模型决定调用 → 工具返回 → 模型据此回答"全过程 | 要加一种 SSE 事件（向后兼容） | ⭐⭐⭐⭐⭐ |
| **C 全透明** | 前端可手动触发工具、看原始 JSON | 最像调试器 | 交互复杂，偏离"聊天界面" | ⭐⭐⭐ |

**我推荐 B。** 理由：这个项目的目标是"让用户学会原理"，而工具调用的原理**恰好就在那个看不见的中间步骤**里。黑盒版本能跑，但学不到东西。

## 3. 路线 B 的契约变更（**这是要用户批的那一条**）

在 README §3 现有两条之后**追加**（不改动已有的，保证向后兼容）：

```
新增（可选）事件：
data: {"tool": {"name": "get_current_time", "status": "calling", "args": {}}}
data: {"tool": {"name": "get_current_time", "status": "done", "result": "2026-11-23 09:20:31"}}
```

**关键设计：加一条"不认识就忽略"的兼容条款**

> 客户端收到无法识别的 `data:` 事件时，必须忽略而不是报错。

这样：老前端（只会读 `delta`）照样能用；新前端能渲染工具卡片。**契约是向后兼容的追加，不是破坏性修改。**

## 4. 后端要做的（你）

1. `tools` 定义（DeepSeek 兼容 OpenAI 格式），先给两个：
   - `get_current_time()` —— 无参数，返回服务器当前时间。**教学上最佳**：模型"不可能自己知道"，对比最明显
   - `calculator(expression)` —— 只支持 `+ - * /` 和括号的表达式，**自己写解析，禁止 `eval`**（红线：不执行任意代码）
2. Agent 循环（教学注释要写透）：
   - 请求带 `tools` → 流式收到 `delta.content` 和 `delta.tool_calls`
   - 出现 `tool_calls` → 攒参数 JSON（**分片到达，要拼**）→ 执行本地函数
   - 把 assistant 的 `tool_calls` 消息 + `role:"tool"` 结果追加回 `messages` → **再请求一次**
   - **硬上限 5 轮**，超了就停下并回一句"工具调用轮数超限"
3. SSE 里按 §3 发工具事件
4. 错误路径：工具抛异常时，把异常信息作为 `tool` 结果回给模型（而不是直接 500），让模型自己解释——这本身就是很好的教学素材

## 5. 前端要做的（我）

1. 解析新增的 `tool` 事件（`realStream` 里加一个分支，仍忽略未知事件）
2. 渲染成气泡下方的**工具卡片**：

```
🔧 调用 get_current_time
   → 结果：2026-11-23 09:20:31
```

3. 视觉上要和普通文字区分（虚线框、等宽字体），让用户一眼看出"这段不是模型说的话"
4. 旧行为不变：`delta` 照旧逐字渲染

## 6. 验收标准（三问就能验）

| 输入 | 期望 |
|---|---|
| "现在几点？" | 出现 `calling` + `done` 两个工具事件 → 回答里的时间与服务器时间一致 |
| "1+1 等于几" | 模型可以自答（**不**触发工具）——证明工具是模型**选择**用的，不是每次都调 |
| "把 20 除以 0 算一下" | 工具返回错误 → 模型用自然语言解释"不能除以零"，**不崩溃** |

加上：轮数上限（故意构造循环）必须停在 5 轮内。
